What the history shows
  1. Every scheduled run exists exactly once and completed: success
     (sync #9 "skipped" at 8fbf468 is its job-level opt-in, before it was
     enabled). run_attempt = 1 everywhere. No run is cancelled, queued,
     waiting or failed.  => concurrency cancellation: NONE observed (a
     pending run superseded in a concurrency group shows as cancelled).
  2. created_at == run_started_at on every run; sampled jobs got a runner in
     1-3 s and finished in about 30-60 s.  => runner queue delay: NONE; run
     overlap: NONE (each run ends minutes before the next one exists).
  3. Scheduled runs use the workflow file on the DEFAULT branch (GitHub docs,
     below). Main's dashboard cron was '41 * * * *' (hourly) from 3d018aa
     (2026-09-21 01:16Z) until the PR #7 merge 63071af (2026-09-24 21:15Z);
     '7,22,37,52 * * * *' (15 min) only since then. The 15-minute cadence
     described on PR #7 did NOT apply to runs #4-#22.
  4. Most cron slots produced no run object at all: dashboard 19 runs for
     92 hourly slots, then 2 runs for 43 quarter-hour slots; sync 30 runs for
     131 hourly slots. Quadrupling the slots did not add runs (about one run
     per 5 h before and after). Where a run did appear it was 1-57 min after
     the nearest earlier slot (lower bound: which slot it served is not
     recorded).
  5. Nothing in the repository can remove a slot: no job-level `if` skipped
     a dashboard run (a skipped run still leaves a run object, like sync #9),
     both workflows are active, the files exist on main, and the repository
     is active (the 60-day public-repo auto-disable does not apply).

Conclusion
  The missing builds are schedule events GitHub never turned into runs. The
  repository-side mechanisms asked about are ruled out by the records above
  (cancellation, queueing, overlap, disabled workflow, skipped jobs, wrong
  branch). GitHub documents that `schedule` events "can be delayed during
  periods of high loads" and that "some queued jobs may be dropped"; that is
  the only documented mechanism left, but GitHub exposes no record of a
  dropped event, so the internal cause (load, per-repository throttling, or
  anything else) is UNKNOWN and not claimed. No timing guarantee follows from
  the cron: observed gaps were 2.0-7.8 h, median about 5 h, for BOTH
  workflows, at any cron density tried.

GitHub documentation read 2026-09-25
  docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows
  (schedule): "The schedule event can be delayed during periods of high
  loads of GitHub Actions workflow runs. High load times include the start of
  every hour. If the load is sufficiently high enough, some queued jobs may
  be dropped." "This event will only trigger a workflow run if the workflow
  file exists on the default branch." "Scheduled workflows will only run on
  the default branch." "The shortest interval you can run scheduled
  workflows is once every 5 minutes." "In a public repository, scheduled
  workflows are automatically disabled when no repository activity has
  occurred in 60 days."
  (workflow_run): fires on "requested" / "completed"; "This event will only
  trigger a workflow run if the workflow file exists on the default branch";
  at most three levels of chaining.
  docs.github.com/en/actions/concepts/security/github_token: events
  triggered by GITHUB_TOKEN create no new run, except workflow_dispatch and
  repository_dispatch (a workflow_run completion is not a GITHUB_TOKEN act).
